# Architecture report — inferred from declared dependencies

A dependency manifest is the architecture stated by the author in machine-readable
form. A package declaring `fastapi`, `celery` and `redis` has an HTTP tier, a worker
tier and a broker, and it has said so more reliably than its documentation will.

Failure points come from combinations rather than from a checklist. `redis` alone is
unremarkable; `redis` serving as both broker and application cache is a specific,
nameable hazard — a routine cache flush destroys queued work — and it is the class of
finding a project's own documentation will not contain.

## Named hazards

**deepeval**
- depends on a single model provider (openai); a provider outage or price change has no fallback path
- long-running model calls inside a synchronous HTTP tier with no worker declared — request timeouts and connection limits become the throughput ceiling well before the model does

## What this method cannot see

A dependency list says what is depended on and nothing about how well it is used. It
cannot see architecture inside a single package, cannot detect a dependency used for
one helper function, and reports absence as absence of a declaration rather than as
absence of the capability. Every claim above is labelled with the manifest that
produced it for exactly that reason.
